# Terraform

Modules for running Launchpad on Google Cloud. They are what the Cloud Run
driver deploys into: an image repository, a database, and the control plane
itself with the identities and permissions it needs to build and release other
people's code.

```bash
cd examples/single-project
cp terraform.tfvars.example terraform.tfvars   # edit it
terraform init
terraform apply
```

The example is a complete install in one project. The modules underneath it are
separate because the pieces have different lifetimes — a database outlives many
control-plane images — and because an install that already has an image
repository or a Postgres instance should be able to use it.

| Module | Creates |
| --- | --- |
| `modules/artifact-registry` | Docker repository with a cleanup policy, and repository-scoped push and pull access |
| `modules/database` | Cloud SQL for PostgreSQL, a database, a generated password, and the connection URL as a Secret Manager secret |
| `modules/control-plane` | Two Cloud Run services from one image, two service accounts, the IAM to deploy, and the Cloud Build staging bucket |

## Why the control plane is two services

The binary serves two listeners: the REST API, and the proxy that routes
`<environment>-<project>.<base-domain>` to whichever workload is currently
serving that environment. Cloud Run publishes one port per service, so the
module runs the same image twice with `LAUNCHPAD_HTTP_ADDR` and
`LAUNCHPAD_PROXY_ADDR` swapped. Only the API service runs deploy workers; a
second set would compete for the same queue for nothing.

Both services set `cpu_idle = false` and keep one instance running. Cloud Run
throttles CPU between requests by default, and both services do work when no
request is in flight — the API polls the deployment queue, and both flush the
minute of metrics they have accumulated. Scaling to zero would mean a queued
deployment is never claimed and the measurements have a hole in them for every
quiet minute. That standing instance is the price of running the deploy workers
in the same process as the API, and it is cheaper than operating a second
deployable.

## Permissions

The control plane's identity gets `run.developer` rather than `run.admin`:
creating and updating services does not require the ability to rewrite their IAM
policies. `iam.serviceAccountUser` is granted on the workload service account
alone, because at project level it would let the control plane act as every
service account in the project, including its own. Build context uploads go to a
bucket the module creates, so write access is scoped to that bucket instead of
the project-wide `storage.admin` the Cloud Build quickstart suggests.

Deployed applications run as a service account created for the purpose and given
nothing at all. The alternative is Google's default compute account, which can
read every bucket in the project — not an identity to hand somebody else's code.

## What these modules do not create

**Wildcard DNS and TLS.** Every environment answers on its own hostname under
`base_domain`, so reaching them needs `*.base_domain` pointed at the proxy
service. Cloud Run domain mappings do not accept wildcards, so this means a
global external load balancer with a serverless NEG and a wildcard certificate.
That belongs with whatever already terminates TLS for your estate, and inventing
one here would be guessing at an answer you already have. `terraform output
proxy_url` is what the record has to reach.

**A state backend.** The database password is generated by Terraform, so it is
in state. State belongs in a versioned bucket with an access policy you chose,
not one a module picked for you.

**The image.** Build it from the repository root with `make image` and push it to
the repository this creates. Name a digest rather than a tag in
`terraform.tfvars` if you want a revision to keep running the bytes it was
created with.

**The first API key.** Minting one needs database access, not cloud access. Run
`launchpad-bootstrap` through the Cloud SQL Auth Proxy using the
`database_connection_name` output.

## Checking a change

```bash
terraform fmt -check -recursive .
cd examples/single-project && terraform init -backend=false && terraform validate
```

`validate` needs the provider downloaded but no credentials, so it runs anywhere
and catches every misnamed argument. It cannot tell you an IAM binding is
insufficient — only an apply into a real project can.

The lock file is not committed. It records which registry the providers came
from, so one written by OpenTofu names `registry.opentofu.org` and breaks
`terraform init`, and the reverse.
